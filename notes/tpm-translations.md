# TPM translations
Q: How does a modern engineering team make sure only reviewed, working code reaches productions, and what would you watch as the TPM?
A: Modern engineering teams utilize Pull Requests and approved Reviewers or Code Owners. This will ensure the proper people review the changes.  As a TPM, I would put suggest client side hooks and define server side rules, as well as monitor the check-in logs.

Model Answer: Every change goes through a short-lived branch and pull request.  Server side rules on main require review and passing automated checks before anything merges, and CODEOWNERS routes changes to the right reviewers.  Because main is always releaseable, teams can ship small changes often instead of batching risky releases.  As the TPM, I'd watch the PR size, time waiting for first review, and how long branches live: big, slow, long-lived PRs are an early warning for integration problems and schedule slips.  I'd also check that the rules are enforces on the server rather than relying on everyone to follow a process. 

Adesso tie-in: At Adesso, I moved the team from SVN to TFS for this exact reason: a single source of truth and a controlled merge/release process.  Over the years, the deployment of individual client customizations wound up with several distinct versions of our application.  Deploys would often overwrite custom code that was deployed in a one-off.  By moving to TFS and enforcing strict check-in processes, I was able to make our release process to Production much smoother without disruption to existing functionality our clients relied on.
